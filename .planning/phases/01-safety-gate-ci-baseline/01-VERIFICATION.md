**What is newly open:** A fresh code re-review (01-REVIEW.md, committed `f30d9ab`) found a third-round CR-01 in the exact mechanism plan 01-13 just rewrote: `mediumIdentity`'s `readdir` error handling doesn't distinguish "directory doesn't exist" from "directory exists but can't be read." I independently reproduced this in this verification pass with a fresh repro script (not a re-run of the reviewer's): `chmod 0o311` (search-only; no read permission for owner, group, or other) on a `test/fixtures/out/bd_movie` copy's `BDMV` directory freezes the computed identity (confirmed byte-identical before and after editing `BDMV/index.bdmv` and `BDMV/PLAYLIST/00000.mpls`), while both vendored parsers (`engine/bin/bdinfo`, which listed all 4 titles, and `engine/bin/ffprobe -playlist 0 -i bluray:<dir>`, which read all 6 real streams) kept working normally on the same tree, because they only need the execute bit the chmod preserved — Node's `readdirSync`, which needs the read bit, is what actually throws `EACCES`. This means probe/rip on a Blu-ray folder whose owner (or an NFS/SMB share admin, or an extracted-archive directory mode) made a subdirectory traverse-only proceed unsandboxed with no new prompt — the exact invariant text this phase exists to guarantee, for a narrower-again precondition (write access to the folder PLUS the ability to change a directory's permission bits, which most local-disk, archive-extraction and many NAS/SMB scenarios allow, but a genuinely read-only mount would not).

**Pattern across all three rounds:** each gap-closure plan has fixed exactly the specific files/paths the previous review named, and each time a fresh review has found a new way to make the walk blind to a subtree it's supposed to cover (round 1: no identity binding at all; round 2: whole directories never walked; round 3: a walked directory silently stops being walked on a permission error). This is consistent with iterating on the narrow fix rather than the walk's error-handling discipline as a whole. The concrete fix 01-REVIEW.md proposes (fail closed on any readdir error other than ENOENT/ENOTDIR) is a small, targeted change, similar in shape to the cap fix from round 2.

**Assessment of the metadata-fingerprint approach vs. WR-10 (requested by task instructions, not itself a blocking gap this round):** Even after CR-01 round 3 is fixed, the review's WR-10 finding stands: the same-disc check runs once, immediately before `spawn()`, but the unsandboxed engine then reads from the folder for the whole rip (minutes to tens of minutes for a Blu-ray), opening each clip's `.m2ts`/`.clpi` or each DVD `VTS_xx_N.VOB` lazily as it's reached. A metadata fingerprint computed at spawn time structurally cannot detect a file changed 30 seconds into a 40-minute rip — that isn't a bug in the walk's coverage or its error handling, it's inherent to checking once before spawn rather than continuously during the read. Closing CR-01 round 3 (and even round 2) narrows the window during which an attacker can make an undetected change to "before the next scan or the next queued job's `start()` re-check," but it does not and cannot close the window that opens the moment `start()`'s check passes and spawn happens. The only mechanisms that remove that residual are ones that make the *read* itself safe regardless of what the folder contains after the check — i.e., the engine sandbox (SF-1/SAFE-11), which stops the unsandboxed parser from running against attacker-controlled bytes in the first place, or continuous re-checking during the rip (which 01-REVIEW.md suggests cheaply as a `close`-handler re-check, catching a *tampered-output* case but not a mid-rip-misread case). Given that framing, the developer has roughly three paths: (a) run another gap-closure round that fixes CR-01 round 3 only (the readdir fail-open, which is a cheap, mechanical, well-specified fix) and explicitly document the WR-10 residual in SECURITY.md as "checked at spawn time, not continuously" so the phase's own claim stops overstating itself; (b) do (a) plus the cheap close-handler re-check WR-10 suggests, as defense in depth against tampered output specifically; or (c) decide the spawn-time check is "good enough" for this phase's goal text given it closes the overwhelming majority of the exposure window, and explicitly scope the "changed mid-rip" residual to the sandbox work (SF-1) in the roadmap/requirements wording rather than treating it as a Phase 1 blocker. Recommend treating CR-01 round 3 (the readdir fail-open) as the blocking gap for this verification regardless of which path is chosen for WR-10, since CR-01 is a mechanical defect in work this phase already committed to shipping, while WR-10 is a design-level residual that the roadmap can legitimately scope elsewhere.
